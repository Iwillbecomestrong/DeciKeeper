# 时间规则、额度与出口规格

> **职责**：本文件定义知止当前两类时间规则（勿扰时段、应用时间窗）以及休息、临时解锁、每周特权、额度结余/借用、冷却和时间规则生效策略的详细契约。
>
> 根 [`SPEC.md`](../../SPEC.md) 保留跨模块原则；本文件是「该停的时候停下来」这一侧的详细规格。

---

## 1. 范围与术语

底部导航统一使用 **「时间规则」**，只包含：

1. **勿扰时段**（DND Segment）
2. **应用时间窗**（App Window）
3. **时间规则生效策略**（只决定前两项修改何时生效）

以下内容虽然与使用限制有关，但**不属于“时间规则”这个页面概念**：

- 黑白名单；
- 全局参数；
- 防卸载 / 防关权限 / 隐私空间 / 闹钟防关机；
- 闹钟任务本身。

---

## 2. 两把锁

### 2.1 勿扰时段锁

勿扰时段回答：

> **一天中的哪些时间，命中限制范围的应用需要被拦截？**

每个时段可以包含：

- 名称；
- 开始/结束时间；
- 生效星期；
- 时段级限制名单；
- 休息额度 / 可用次数等与该时段相关的参数。

勿扰时段之间的空白区间称为 **空档期（Gap）**。空档期表示勿扰锁没有激活，但**不代表所有限制都消失**：应用时间窗仍可继续生效。

### 2.2 应用时间窗锁

应用时间窗回答：

> **某些高风险应用只允许在一天中的哪些时间使用？**

对被时间窗管理的应用：

- 时间窗外：正常路径下阻止启动或继续使用；
- 时间窗内：只表示“时间窗这把锁允许”，不代表勿扰锁自动解除。

当前 `AppWindowManager` 的组合语义可以概括为：

> **被时间窗管理的应用，普通使用需要同时满足「当前在允许时间窗内」以及「勿扰锁已因休息或空档而解除」。**

因此两把锁是 **AND** 关系，不是“任意一把允许就放行”。

### 2.3 两把锁与三个出口

| 状态 / 出口 | 勿扰时段锁 | 应用时间窗锁 |
| --- | --- | --- |
| 空档期 | 不生效 | 仍可能生效 |
| 休息 | 临时解除 | **不解除** |
| 临时解锁 | 可短暂越过 | 可短暂越过 |
| 每周特权 | 可越过 | 可越过 |

## 3. 休息（Rest）

休息是最常用、最轻量的出口。

### 3.1 作用范围

- 只解除勿扰时段锁；
- 不解除应用时间窗；
- 结束后重新回到原规则约束；
- 休息本身受额度、次数、冷却与借用规则约束。

### 3.2 加权额度区间

当前实现不是旧文档中“≤3 分钟扣 0.5 次、>3 分钟扣 1 次”的固定阈值模型。

请求覆盖的时间被按状态拆成不同权重：

| 区间 | 权重 |
| --- | ---: |
| 空档 / 已经处于休息 | 0 |
| 普通勿扰区间 | 1 |
| 与冷却期重叠的勿扰区间 | 2 |

核心含义：

- 已经自由的区间不重复收费；
- 正常受限区间按正常成本收费；
- 冷静期内再次申请，对实际重叠部分提高成本；
- 不能因为请求里“有一点冷却重叠”就把整段全部按双倍算。

### 3.3 当前量化与次数折算

当前 JVM 测试守护以下行为：

1. 每个计费区间先量化到 UI 使用的一位小数分钟颗粒度，再应用权重；
2. 加权额度成本 = 普通勿扰区间 × 1 + 冷却重叠区间 × 2；自由区间 × 0；
3. 次数成本根据加权成本相对于本次请求时长计算，结果按 half-up 取整并限制在 `0..2`；
4. 全空档 / 全休息可得到 0 次；全普通勿扰为 1 次；全冷却可到 2 次；混合区间按实际比例计算。

详细算法以 `WeightedRestCountTest` 及其对应纯函数为实现守护，修改时必须同步更新测试和本规格。

## 4. 临时解锁（Temporary Access）

用户侧正式名称统一为 **「临时解锁」**。

不得再把以下名称作为新用户文案：

- 超级临时；
- 超级临时放行；
- 临时放行。

### 4.1 作用

临时解锁用于处理非常短的临时需求，例如：

- 验证码；
- 扫码；
- 临时联系；
- 短时间处理被两把锁阻挡的必要操作。

它可以短暂越过：

- 勿扰时段锁；
- 应用时间窗锁。

### 4.2 休息额度扣费的状态条件

临时解锁**不是永远免费，也不是永远收费**。

当前确定规则：

| 当前状态 | 是否重复消耗休息额度 |
| --- | --- |
| 勿扰空档期 | **不消耗** |
| 已经处于休息 | **不消耗** |
| 勿扰时段、未休息 | 消耗 |
| 冷却区间 | 对实际受限/冷却重叠部分按当前加权规则处理 |
| 仅“时间窗外” | 是否扣休息额度取决于同时是否处于空档 / 休息 / 勿扰等状态 |

因此文档和 UI 不得简化为“临时解锁不消耗额度”。

### 4.3 冷却与二级应急

临时解锁结束后可进入临时解锁冷却。当前实现还保留冷却期内的短时二级应急能力，用于扫码等极短需求。

具体秒数、等待次数和上限属于可变实现参数，不在总规格中写死；若这些参数需要成为稳定产品承诺，应由全局参数与对应测试共同定义。

## 5. 每周特权（Privilege）

每周特权是比休息和临时解锁更稀缺、持续时间更长的例外出口。

当前稳定契约：

- 可越过勿扰时段锁；
- 可越过应用时间窗锁；
- 不消耗普通休息额度，而消耗独立的特权配额；
- 受每周次数、总时长和可用时段约束；
- 额度按周刷新。

总规格不把“固定 1~2 次”“固定 480 分钟”等某一时刻的 UI 参数写成永久产品规则。当前输入上限和默认值若需记录，应放在实现/验收文档中。

## 6. 额度结余与借用

### 6.1 同一业务日内结余

未使用的休息额度可以向后续时段结余。

结余的核心目的是：

> **白天少用一点，后面仍然可以把此前没有使用的自由留给自己。**

结余只在同一逻辑 / 业务日内流转，不应把上一业务日的剩余额度永久滚存成跨日资产。

### 6.2 从下一时段借用

当前时段额度不足时，可以按规则从**同一业务日的下一时段**预支。

稳定契约：

- 借用存在上限，比例由全局参数控制；
- 借用会对下一时段产生惩罚性扣减；
- 当前产品口径是 **借 1，下一时段扣 2**；
- 下一时段属于下一业务日时，不应继续显示为可借额度；
- 已借额度必须作为“负担/未来扣减”展示，不能再次被当作当前可消费余额。

## 7. 冷却（Cooling）

冷却的目的不是增加一个新的锁，而是避免用户连续、无间隔地重复申请出口。

当前存在至少两类相关冷却来源：

- 休息结束后的冷却；
- 临时解锁结束后的冷却。

稳定语义：

- 申请区间与冷却实际重叠的部分提高额度成本；
- 未重叠部分仍按正常权重处理；
- UI 应在用户确认前说明本次实际成本，不应扣费后才提示；
- 冷却状态不得覆盖掉“当前本来已经处于空档/休息”的免费区间语义。

## 8. 时间规则生效策略

时间规则额外提供两种修改生效策略。

### 8.1 作用范围

**只控制：**

- 勿扰时段；
- 应用时间窗。

**不控制：**

- 黑白名单；
- 全局参数；
- 防卸载；
- 防关权限；
- 隐私空间；
- 闹钟防关机；
- 其他保护能力。

### 8.2 宽严有别（默认 / 推荐）

- 加严：立即生效；
- 放宽：下一刷新时刻生效。

加严 / 放宽必须按“最终限制是否更强”判断，而不是按“增加/删除一条数据”字面判断。

例如应用时间窗是**允许窗口**：

- 缩短允许窗口 = 加严；
- 延长允许窗口 = 放宽。

### 8.3 全部次日

- 勿扰时段修改：全部在下一刷新时刻生效；
- 应用时间窗修改：全部在下一刷新时刻生效。

“下一刷新时刻”跟随知止业务日边界，不等价于固定 `00:00`。

### 8.4 策略切换

切换策略时，`EffectiveActivationPolicyManager` 会要求 `TimeRuleManager` 与 `AppWindowManager` 重新协调 active / pending 状态，避免单纯切换 UI 文案却留下与新策略矛盾的 pending 数据。

## 9. 正常规则之外的即时纠错例外

“加严立即、放宽延期”描述的是**正常保护期的主规则**，不是无条件覆盖所有场景的绝对句。

### 9.1 适应期

当前代码在适应期对时间规则修改提供更宽松的即时纠错路径，使新用户可以先把配置调到合适状态。

因此文档不得写成：

> “任何放宽在任何时候都绝对无法立即生效。”

### 9.2 Fresh Segment / Regret Period

当前勿扰时段不利变更分析包含 Fresh Segment Exemption：刚建立、仍处于当前“新鲜规则/反悔期”语义中的时段，不完全按已经稳定的 baseline 覆盖判定。

它的目的与适应期类似：

- 防止刚创建一个明显配置错误的时段后立刻被长期锁住；
- 只对尚未稳定建立的规则提供即时纠错；
- 已稳定的既有规则仍按正常保护逻辑处理。

具体 freshness 判定算法由 `SegmentAdverseAnalysis` 和相关测试定义。

## 10. 业务日与刷新边界

时间规则、额度、结余、借用和 pending 必须共享同一业务日概念。

当前实现以规则边界推导业务日，而不是机械使用自然日 `00:00 → 24:00`。跨午夜的勿扰时段应归属于它开始时所在的业务日，避免：

- 深夜额度被午夜清零；
- 借用跨到错误日期；
- pending 与统计按不同“今天”计算。

业务日边界的底层算法如需调整，必须同时审计：

- TimeRuleManager；
- CreditManager；
- ConfigPendingManager；
- 统计聚合边界；
- 首页额度展示。

## 11. 当前组合状态验收表

以下表格只描述普通规则与三个出口的产品语义，不替代具体额度算法。

| 当前状态 | 普通受 DND 应用 | 被 App Window 管理的应用 | 休息 | 临时解锁 | 每周特权 |
| --- | --- | --- | --- | --- | --- |
| DND 中，未休息，时间窗外 | 锁 | 锁 | 仅解除 DND | 可短暂越过 | 可越过 |
| DND 中，未休息，时间窗内 | 锁 | **仍锁（DND 未解除）** | 解除 DND 后时间窗应用可用 | 可短暂越过 | 可越过 |
| DND 中，已休息，时间窗外 | DND 已解除 | **仍被时间窗锁** | 已在休息 | 临时解锁不重复扣休息额度 | 可越过 |
| DND 中，已休息，时间窗内 | DND 已解除 | 可用 | 已在休息 | 不重复扣休息额度 | 可越过 |
| 空档，时间窗外 | 可用 | 被时间窗锁 | DND 本来已解除 | 临时解锁不扣休息额度 | 可越过 |
| 空档，时间窗内 | 可用 | 可用 | DND 本来已解除 | 不扣休息额度 | 可越过 |

## 12. 文档与测试红线

以下旧说法不得重新写回当前规格：

- “休息 ≤3 分钟固定扣 0.5 次，>3 分钟固定扣 1 次”；
- “临时解锁永远不消耗额度”；
- “应用时间窗内就一定可以使用”；
- “休息可以解除应用时间窗”；
- “延长应用允许时间窗属于加严”；
- “全部次日会控制黑名单、全局参数和保护功能”；
- 用户侧继续使用“超级临时”作为正式名称。

核心行为修改必须有对应测试守护，至少覆盖：

- DND / Gap / Rest 与 App Window 的组合；
- 加权额度和次数；
- 临时解锁在 Gap / Rest 免费、其他状态计费；
- 冷却实际重叠区间；
- 同业务日结余与跨业务日借用边界；
- 两种时间规则生效策略；
- 适应期和 Fresh Segment 例外。
