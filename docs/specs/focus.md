# 时间规则、额度与出口规格

> **职责**：本文件定义知止当前两类时间规则（勿扰时段、应用时间窗）以及休息、临时解锁、每周特权、额度结余/借用、冷却和时间规则生效策略的详细契约。
>
> 根 [`SPEC.md`](../../SPEC.md) 保留跨模块原则；本文件是「该停的时候停下来」这一侧的详细规格。

---

## 1. 范围与术语

底部导航统一使用 **「时间规则」**，只包含：

1. **勿扰时段**（DND Segment）
2. **应用时间窗**（App Window）
3. **时间规则生效策略**（只决定前两项修改何时生效）

以下内容虽然与使用限制有关，但**不属于“时间规则”这个页面概念**：

- 黑白名单；
- 全局参数；
- 防卸载 / 防关权限 / 隐私空间 / 闹钟防关机；
- 闹钟任务本身。

用户侧三个出口统一称为：

> **休息 / 临时解锁 / 每周特权**

其中「临时解锁」是正式用户术语；新文案不得再使用「超级临时」「超级临时放行」「临时放行」。

## 2. 两把锁

### 2.1 勿扰时段锁

勿扰时段回答：

> **一天中的哪些时间，命中限制范围的应用需要被拦截？**

每个时段可以包含名称、开始/结束时间、生效星期、时段级限制名单以及休息额度 / 可用次数等参数。

勿扰时段之间的空白区间称为 **空档期（Gap）**。空档期表示勿扰锁没有激活，但**不代表所有限制都消失**：应用时间窗仍可继续生效。

### 2.2 应用时间窗锁

应用时间窗回答：

> **某些高风险应用只允许在一天中的哪些时间使用？**

对被时间窗管理的应用：

- 时间窗外：正常路径下阻止启动或继续使用；
- 时间窗内：只表示“时间窗这把锁允许”，不代表勿扰锁自动解除。

当前组合语义可以概括为：

> **被时间窗管理的应用，普通使用需要同时满足「当前在允许时间窗内」以及「勿扰锁当前没有继续阻挡」。**

因此两把锁是 **AND** 关系，不是“任意一把允许就放行”。

### 2.3 两把锁与三个出口

| 状态 / 出口 | 勿扰时段锁 | 应用时间窗锁 |
| --- | --- | --- |
| 空档期 | 不生效 | 仍可能生效 |
| 休息 | 临时解除 | **不解除** |
| 临时解锁 | 可短暂越过 | 可短暂越过 |
| 每周特权 | 可越过 | 可越过 |

### 2.4 主页系统状态呈现契约（Home Status Pill）

主页采用底部的状态胶囊条作为系统运行状态的**单一真相呈现中心**，彻底废除左上角独立的状态悬浮行（`tv_temp_access_status`），消除冷却期上下重复与突兀感：

- **空档期（Gap）**：未在勿扰时段且无临时解锁/冷却时，常驻展示 `🍃 空档期`（`zzSuccess` 主题色）；
- **勿扰中（DND Active）**：处于勿扰时段且无临时解锁/冷却时，常驻展示 `🔒 勿扰中`（`zzMuted` 主题色）；
- **临时解锁中（Temporary Access Active）**：临时解锁生效期内，展示 `🟡 临时解锁中 还剩 Xmin Ys`（`zzWarning` 主题色）；
- **冷却期（Cooling Active）**：根据冷却主要来源智能匹配，展示 `🔒 临时解锁冷却 还剩 Xs` 或 `⏳ 休息冷却中 还剩 Xs`（`zzWarning` 主题色）；
- **休息中（Resting / Privilege）**：胶囊条自动隐藏，由下方操作大卡片单独负责倒计时与“结束当前休息”交互，避免同屏卡片视觉重复。

## 3. 休息（Rest）

休息是最常用、最轻量的出口。

### 3.1 作用范围

- 只解除勿扰时段锁；
- 不解除应用时间窗；
- 结束后重新回到原规则约束；
- 休息本身受额度、次数、冷却与借用规则约束。

### 3.2 当前次数基础规则

当前 `dev` 已重新收敛为按**本次申请时长分档**的基础次数模型：

| 本次申请时长 | 基础次数成本 |
| --- | ---: |
| `≤ 3 分钟` | `0.5 次` |
| `> 3 分钟` | `1.0 次` |

代码内部使用 half-unit 表示次数，因此 `0.5 次 = 1 half-unit`，`1.0 次 = 2 half-units`。

这一定义描述的是**基础次数**。冷却和借用可能进一步提高最终成本。

### 3.3 冷却采用整单倍率

最新实现已经从“按冷却实际重叠的若干秒分段加权”切换为更容易理解和展示的**整单倍率**。

正常情况下：

- 本次应计费时长按 `×1` 计算；
- 次数按 3.2 的基础档位计算。

当发起申请时已经处于相关冷却状态：

- 当前应计费申请按 `×2` 计算；
- 基础次数也整体 `×2`；
- 不再因为冷却只剩少量秒数，就只给那几秒做比例加权。

因此典型次数结果为：

| 本次申请 | 正常 | 冷却中 |
| --- | ---: | ---: |
| `≤ 3 分钟` | `0.5 次` | `1.0 次` |
| `> 3 分钟` | `1.0 次` | `2.0 次` |

`WeightedRestCountTest` 中保留的旧比例 helper 测试属于兼容 / 历史纯函数覆盖；**新产品契约以当前主计费路径的“时长分档 + 整单倍率”为准**。如果后续仍有边缘分支继续调用旧比例 helper，应作为实现收敛问题处理，而不是重新把旧模型写回产品规格。

### 3.4 确认前必须展示真实成本

用户确认休息前，UI 应尽可能展示本次将产生的：

- 当前额度扣减；
- 当前次数扣减；
- 是否触发冷却倍率；
- 是否需要从后续时段借用；
- 借用后对后续时段的实际扣减。

不得先扣费、再用事后提示解释成本。

## 4. 临时解锁（Temporary Access）

### 4.1 作用

临时解锁用于处理非常短的临时需求，例如验证码、扫码、临时联系或短时间处理被两把锁阻挡的必要操作。

它可以短暂越过：

- 勿扰时段锁；
- 应用时间窗锁。

### 4.2 免费与收费的状态条件

临时解锁**不是永远免费，也不是永远收费**。

用户已经确认、当前实现应持续守护的核心规则是：

> **只有在空档期和已经处于休息状态时，临时解锁不消耗休息额度。**

| 当前状态 | 是否消耗休息额度 |
| --- | --- |
| 勿扰空档期 | **不消耗** |
| 已经处于休息 | **不消耗** |
| 勿扰时段、未休息 | 消耗 |
| 冷却中且仍有应计费 DND 部分 | 按整单冷却倍率计费 |
| 仅“应用时间窗外” | 取决于同时处于空档 / 休息 / 勿扰中的哪一种状态 |

因此文档和 UI 都不得简化为“临时解锁不消耗额度”。

### 4.3 免费区间与应计费区间

当前临时解锁计费快照会先区分：

- 已经自由的部分（例如空档 / 已休息）：不重复收费；
- 仍然属于勿扰限制的部分：作为应计费部分。

若全部请求都处于免费状态，则时间与次数成本都应为 0。

若仍存在应计费 DND 部分：

- 正常状态按 `×1`；
- 发起申请时已经处于相关冷却状态时，该**应计费部分整体 `×2`**；
- 次数基础档位仍由本次申请时长决定，再应用相同倍率。

这与旧的“只把冷却剩余几秒乘 2”模型不同。

### 4.4 冷却与二级应急

临时解锁结束后可进入临时解锁冷却。当前实现还保留冷却期内的短时二级应急能力，用于扫码等极短需求。

具体秒数、等待次数和输入上限属于可变实现参数；只有在准备把这些数字变成稳定产品承诺时，才应写入本规格并增加对应测试。

## 5. 每周特权（Privilege）

每周特权是比休息和临时解锁更稀缺、持续时间更长的例外出口。

稳定契约：

- 可越过勿扰时段锁；
- 可越过应用时间窗锁；
- 不消耗普通休息额度，而消耗独立的特权配额；
- 受每周次数、总时长和可用时段约束；
- 额度按周刷新。

总规格不把“固定 1~2 次”“固定 480 分钟”等某一版本的输入值写成永久铁律。当前上限若需要对外承诺，必须由 UI 校验、业务逻辑与测试共同守护。

---

## 6. 额度结余与借用

### 6.1 同一业务日内结余

未使用的休息额度可以向后续时段结余。

其核心目的不是鼓励把手机时间用满，而是允许：

> **白天少用一点，把没有用掉的自由留给同一天后面真正想休息的时候。**

结余只在同一逻辑 / 业务日内流转，不把上一业务日的剩余额度永久滚存成跨日资产。

### 6.2 从下一时段借用

当前时段额度不足时，可以按规则从**同一业务日的下一时段**预支。

稳定契约：

- 借用存在上限，比例由全局参数控制；
- 当前产品口径是 **借 1，下一时段扣 2**；
- 借用成本应在确认前展示；
- 下一时段属于下一业务日时，不应继续显示为可借额度；
- 已借额度属于未来负担，不能再次被当成当前可消费余额。

冷却 `×2` 与借用“借 1、后续扣 2”是两个不同概念：前者是当前申请的倍率，后者是跨时段预支的偿还规则，UI 和文档不得混为一谈。

## 7. 冷却（Cooling）

冷却的目的不是增加一把新锁，而是避免用户连续、无间隔地反复申请出口。

当前存在至少两类相关冷却来源：

- 休息结束后的冷却；
- 临时解锁结束后的冷却。

当前产品级语义：

- 发起新的应计费申请时，如果已经处于相关冷却状态，本次应计费申请采用整单 `×2` 成本；
- 不再采用“冷却还剩多少秒，就只把多少秒乘 2”的碎片化比例模型；
- 已经处于空档或休息的免费状态不能因为冷却存在而被重复收费；
- UI 必须在确认前说明是否进入双倍成本。

如果未来要恢复比例加权，必须作为明确的产品规则变更处理，同时修改规格、UI 说明和测试，不能只改某个 helper。

## 8. 时间规则生效策略

### 8.1 作用范围

时间规则生效策略**只控制**：

- 勿扰时段；
- 应用时间窗。

它**不控制**黑白名单、全局参数、防卸载、防关权限、隐私空间、闹钟防关机等其他能力；这些能力继续按各自规则生效。

### 8.2 宽严有别（默认 / 推荐）

- **加严：立即生效；**
- **放宽：下一刷新时刻生效。**

加严 / 放宽必须按“最终限制是否更强”判断，而不是按“增加/删除一条数据”字面判断。

例如应用时间窗是**允许窗口**：

- 缩短允许窗口 = 加严；
- 延长允许窗口 = 放宽。

### 8.3 全部次日

- 勿扰时段修改：全部在下一刷新时刻生效；
- 应用时间窗修改：全部在下一刷新时刻生效。

“下一刷新时刻”跟随知止业务日边界，**不等价于固定 `00:00`**。

### 8.4 策略切换

切换策略时，`EffectiveActivationPolicyManager` 要求 `TimeRuleManager` 与 `AppWindowManager` 重新协调 active / pending 状态，避免只切换 UI 文案而留下与新策略矛盾的待生效数据。

## 9. 正常保护期之外的即时纠错例外

“加严立即、放宽延期”描述的是**正常保护期的主规则**，不是无条件覆盖所有场景的绝对句。

### 9.1 适应期

当前代码在适应期允许更宽松的即时纠错，使新用户可以先把规则调到可用状态。因此不得写成“任何放宽在任何时候都绝对无法立即生效”。

### 9.2 Fresh Segment / Regret Period

勿扰时段的不利变更分析包含 Fresh Segment Exemption。刚建立、仍处于当前新鲜规则 / 反悔期语义中的时段，不完全按已经稳定的 baseline 覆盖判定。

其目标是允许修正刚创建就发现明显错误的规则，而不是给已经稳定的旧规则提供即时逃逸口。具体 freshness 判定由 `SegmentAdverseAnalysis` 与对应测试定义。

---

## 10. 业务日与刷新边界

时间规则、额度、结余、借用和 pending 必须共享同一业务日概念。

当前实现以规则边界推导业务日，而不是机械使用自然日 `00:00 → 24:00`。跨午夜的勿扰时段应归属于它开始时所在的业务日，避免：

- 深夜额度被午夜错误清零；
- 借用跨到错误日期；
- pending 与其他业务状态对“今天”的理解不一致。

业务日算法如需调整，必须同时审计 `TimeRuleManager`、`CreditManager`、`ConfigPendingManager`、首页额度展示以及依赖该边界的统计聚合。

## 11. 当前组合状态验收表

| 当前状态 | 普通受 DND 应用 | 被 App Window 管理的应用 | 休息 | 临时解锁 | 每周特权 |
| --- | --- | --- | --- | --- | --- |
| DND 中，未休息，时间窗外 | 锁 | 锁 | 仅解除 DND | 可短暂越过并按规则计费 | 可越过 |
| DND 中，未休息，时间窗内 | 锁 | **仍锁（DND 未解除）** | 解除 DND 后时间窗应用可用 | 可短暂越过并按规则计费 | 可越过 |
| DND 中，已休息，时间窗外 | DND 已解除 | **仍被时间窗锁** | 已在休息 | 临时解锁不重复扣休息额度 | 可越过 |
| DND 中，已休息，时间窗内 | DND 已解除 | 可用 | 已在休息 | 不重复扣休息额度 | 可越过 |
| 空档，时间窗外 | 可用 | 被时间窗锁 | DND 本来已解除 | 临时解锁不扣休息额度 | 可越过 |
| 空档，时间窗内 | 可用 | 可用 | DND 本来已解除 | 不扣休息额度 | 可越过 |

## 12. 文档与测试红线

以下说法不得重新写回当前规格或新用户文案：

- “临时解锁永远不消耗额度”；
- “应用时间窗内就一定可以使用”；
- “休息可以解除应用时间窗”；
- “延长应用允许时间窗属于加严”；
- “宽严有别 = 放宽立即、加严次日”；
- “下一刷新时刻固定等于 00:00”；
- “冷却只把实际重叠的几秒按比例加权”作为当前主计费规则；
- “全部次日会控制黑名单、全局参数和保护功能”；
- 用户侧继续使用“超级临时”作为正式名称。

核心行为修改必须有测试守护，至少覆盖：

- DND / Gap / Rest 与 App Window 的组合；
- `≤3 分钟 0.5 次 / >3 分钟 1 次`的基础次数分档；
- 冷却状态下整单倍率；
- 临时解锁在 Gap / Rest 免费、其他状态计费；
- 同业务日结余与跨业务日借用边界；
- 两种时间规则生效策略；
- 适应期和 Fresh Segment 例外。
