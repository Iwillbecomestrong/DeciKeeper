# 加强约束与保护机制规格

> **职责**：本文件定义决定守护当前「加强约束功能」的详细产品契约、状态语义与系统边界。
>
> 根 [`SPEC.md`](../../SPEC.md) 只保留跨模块原则；本文件是保护模块的详细规格。Android/OEM 页面识别细节以当前代码与测试为实现证据，不能把某一厂商当前页面结构当作永久平台协议。

---

## 1. 模块定位

加强约束功能的目的不是永久阻止用户退出，而是：

> **降低用户通过卸载、关闭关键权限、隐私空间或关机等路径，立刻推翻此前决定的可能性。**

这些功能与「时间规则」是两个层级：

- **时间规则**回答：勿扰时段和应用时间窗什么时候工作；
- **加强约束**回答：已经决定好的规则如何降低被系统入口即时绕过的概率。

因此：

1. 「宽严有别 / 全部次日」**只属于时间规则**；
2. 防卸载、防关权限、隐私空间、闹钟防关机分别遵循自己的状态机；
3. 不承诺“绝对不可绕过”，只持续补强真实发现的绕过路径；
4. 所有保护必须保留用户最终退出权。

## 2. 无障碍服务：技术基础，不是时间规则

Android 无障碍服务是多个保护能力和前台可见性感知的执行基础。

当前职责包括但不限于：

- 接收前台窗口 / 内容变化事件；
- 获取可用的窗口树和可见应用信息；
- 辅助小窗、分屏、PIP 等场景的 Presence Tracking；
- 识别与决定守护相关的系统设置、卸载、强行停止、权限关闭、隐私空间等页面；
- 在符合具体保护开关门禁时执行返回桌面、覆盖层或其他拦截动作。

### 2.0 界面内容读取边界

- 普通第三方应用仅提供时间规则所需的包名、窗口可见性和页面类名信号，不读取事件文字或遍历正文控件；窗口根节点仅用于确认所属包名。
- 保护内容读取只允许已适配的桌面、设置、安装/卸载器、应用商店、手机管家、权限管理及隐私空间组件；保留系统对话框和当前默认桌面。
- 第三方卸载工具以系统授予的 `REQUEST_DELETE_PACKAGES` / `DELETE_PACKAGES` 权限识别，纳入卸载检测；不因包名包含 settings、security、launcher 等单词就扩大内容读取范围。
- 在读取事件文字或请求防护窗口树之前检查来源包，取得窗口后再次检查所属包；不对任意当前界面做节点文字预热。
- 网页应用识别保留包名与页面类名路径，不再以普通应用的事件正文匹配放行关键词。
- 此边界收窄内容使用，不代表系统不再投递跨应用事件，也不保证消除 OEM 的无障碍安全提示。

### 2.1 概念分层与独立防关

| 概念 | 含义与管辖边界 |
| --- | --- |
| **系统无障碍服务** | Android 系统真正授予/撤销的 AccessibilityService 权限与服务连接状态 |
| **无障碍防关保护** | 由 `AccessibilityControlManager` 独立管理。**开启无障碍服务即刻激活**，专门拦截系统设置中关闭该服务的操作；关闭必须在 App 内发起 |
| **防卸载与防关权限保护** | 由 `AntiUninstallManager` 独立管理。管辖应用详情页（强行停止/卸载）与其他系统权限（悬浮窗/自启动/后台弹窗等），**不负责管辖无障碍界面** |

### 2.2 意图持久保留与非正常断连自愈

- **意图不因掉线抹除**：当无障碍服务发生非预期解绑（系统杀后台、APK 覆盖安装瞬态 unbind、系统 Bug 等）时，各个保护模块的持久化配置（`desiredEnabled`）**绝不被擦写为 false**；
- **运行态挂起与重连自愈**：断连期间，各保护模块进入暂挂态（`SUSPENDED`，隐藏浮窗、释放覆盖层，不执行无能力的动作）；一旦无障碍服务重连，自动恢复活跃运行态（`ACTIVE`），用户无需重新开启；
- **严格基准与次日生效**：
  - 系统设置页一律拦截关闭无障碍服务，用户无法在系统设置内直接关闭；
  - 若在 App 内申请关闭：若处于**适应期**或**历史基准为未开启**，允许立即关闭并临时授权放行跳转系统设置；
  - 若已确立基准且非适应期：关闭属于不利操作，App 内**必须且只能走严格次日延迟生效流程**；
  - 在 App 内关闭无障碍时，联动提示并将依赖它的 5 项保护功能一并提交关闭（立即关闭或次日生效）。

### 2.3 Transient 覆盖层代际隔离与防死锁铁律

- **代际强绑定**：锁屏输入面板（密码/时长输入）、申请休息及临时解锁等 transient overlay，必须严格与 `accessibilityGeneration` 绑定。当无障碍服务被系统短暂解绑（如 vivo 快捷支付/安全沙盒触发的 `onUnbind`）并重新连接后，必须立即清理旧代际残留的 transient 窗口；
- **保护链不可剥夺**：输入面板打开（`isInputPanelOpen`）仅允许用于跳过黑名单重度节点扫描以提升打字流畅度，**严禁阻断 `ProtectionManager` 对系统设置页、安装器与防关权限等核心事件的消费**；
- **自愈与门禁倒置防范**：前台监控轮询必须将失效锁包名清理前置于 pause 门禁之前；transient overlay 必须配备 60 秒最大安全超时自愈机制，杜绝 pause 标志残留导致整个前台检测循环发生不可逆死锁。

## 3. 防卸载保护

### 3.1 目标

防卸载保护用于降低通过系统应用信息页、卸载确认、强行停止等路径即时移除或停用决定守护的可能性。

它保护的核心不是“永远不允许卸载”，而是：

> **不让一时冲动立刻把保护本身拆掉。**

### 3.2 状态机

`AntiUninstallManager` 当前状态：

| 状态 | 业务语义 | 是否继续保护 |
| --- | --- | --- |
| `DISABLED` | 防卸载关闭 | 否 |
| `ACTIVE` | 防卸载正常开启 | 是 |
| `PENDING` | 已申请关闭，等待严格下一业务日生效 | **是** |

状态流转：

- `DISABLED → ACTIVE`：立即；
- `ACTIVE → PENDING`：正常保护期内申请关闭；
- `PENDING → DISABLED`：到达 pending 生效时刻；
- `PENDING → ACTIVE`：用户重新开启时取消 pending；
- 适应期内关闭，或只是恢复到“基线本来就是关闭”的状态：可直接进入 `DISABLED`。

正常保护期的关闭使用 `strictNextDay = true`，避免凌晨提交后在同一个自然日上午就提前放开。

### 3.3 当前执行范围

当前实现持续维护以下防绕过路径：

- 决定守护应用信息/卸载相关系统入口；
- 强行停止相关系统对话框；
- 决定守护自身无障碍详情/停止服务相关入口；
- 进程启动、服务重连与 OEM 页面切换中的短暂真空期；
- 与隐私空间相关的已确认特殊入口。

强行停止与普通卸载属于同等级的重要绕过入口，不能因为对话框文字、厂商样式或焦点变化就降级为仅靠文本猜测。

### 3.4 无障碍页面边界

普通“无障碍服务列表”不能被决定守护整体锁死，否则会妨碍用户管理其他 App 的无障碍服务。

保护应聚焦于：

- 决定守护自己的无障碍详情页；
- 停止/关闭决定守护服务的确认路径；
- 已确认会直接削弱决定守护保护链的系统入口。

### 3.5 设备管理器冗余边界

设备管理器是防卸载的可选系统级冗余，不是无障碍防护的替代品，也不作为所有品牌的通用能力承诺。当前产品规则如下：

| 组合状态 | 设置页表现 | 业务含义 |
| --- | --- | --- |
| vivo/iQOO + `DISABLED` + 未激活 | 默认隐藏 | 不向该机型默认推荐冗余能力 |
| 任意品牌 + `ACTIVE` + 未激活 | 显示“需激活” | 业务保护意图已开启，但系统授权尚未成立 |
| 任意品牌 + `ACTIVE`/`PENDING` + 已激活 | 显示且保持勾选 | 设备管理器继续作为冗余保护；`PENDING` 期间不能提前放行 |
| 任意品牌 + `DISABLED` + 已激活 | 显示“可解除” | 业务保护已关闭/到期，用户可前往系统设置手动取消激活 |
| 任意品牌 + `DISABLED` + 未激活 | 显示或隐藏推荐项 | 不代表系统授权存在 |

系统授权页返回后必须重新读取 `DevicePolicyManager.isAdminActive`；打开页面、点击开关或品牌识别都不能替代该事实。设备管理器取消激活路径必须保留，且不得把无障碍服务列表整体拦截。OPPO/ColorOS 的推荐依据仅限已有实测环境；vivo/iQOO 不默认推荐；其他品牌与 ROM 均标记为未验证。

## 4. 防关权限保护

### 4.1 目标

防关权限保护用于降低用户直接进入系统设置，把决定守护赖以执行规则的关键无障碍能力立即关闭的可能性。

### 4.2 状态机

`AccessibilityControlManager` 当前状态：

| 状态 | 业务语义 | 是否继续保护 |
| --- | --- | --- |
| `ACTIVE` | 防关权限保护开启 | 是 |
| `PENDING` | 已申请关闭，尚未到生效时刻 | **是** |
| `DISABLED` | 业务保护关闭 | 否 |

当前规则：

- 开启：立即生效并清除旧 pending；
- 关闭：若在适应期内或**基准状态原本为关闭（恢复基准）**，立即关闭进入 `DISABLED`；若基准状态为开启，提交严格下一业务日的 pending；
- pending 到期后落地为 `DISABLED`；
- `PENDING` 期间系统设置页保护仍按开启状态执行。

### 4.3 与各依赖保护的协同关闭（含桌面守护小浮窗）

用户关闭无障碍服务时，系统将一并联动提交所有依赖无障碍的保护能力（防卸载与防关权限、桌面守护小浮窗、小窗可见性增强、隐私空间拦截、闹钟防关机）的关闭操作：
- 各子功能遵循统一的「恢复基准立即关闭 / 维持基准次日生效」判定；
- 确认弹窗动态呈现各子功能的实时生效时间（若全部项基准均为关，则提示“立即全部解除”并引导前往系统设置关闭服务）；
- 若系统无障碍服务被外部或用户直接停用，底层 `AccessibilityDependencyManager` 立即联动卸载桌面守护小浮窗，杜绝僵尸悬浮。

这体现的仍是同一原则：

> **允许退出，但不给冲动提供逐层秒拆保护链的捷径。**

### 4.4 扩展保护覆盖范围（自启动、关联启动、悬浮窗与 Vivo 累计后台弹窗）

为了防止用户通过关闭「自启动」、「关联启动」、「悬浮窗」权限或在厂商系统管家中执行「管控/卸载」间接削弱决定守护的后台存活与防卡片强杀能力，防护逻辑在「防关权限保护」开启（`ACTIVE` 或 `PENDING`）时自动延伸至上述权限及管控入口：

- **生效条件**：在主流系统设置与手机管家包名（如 `com.android.settings`, `com.miui.securitycenter`, `com.vivo.permissionmanager`, `com.vivo.imanager`, `com.vivo.abe`, `com.iqoo.secure`, `com.coloros.safecenter` 等）下：
  1. 页面标题/分类特征包含 `自启动` / `自动启动` / `关联启动` / `关联唤醒` / `悬浮窗` / `后台弹窗` / `累计后台弹窗` / `管控`（及多语言等价词汇）；
  2. 无障碍节点在当前屏幕或视图树中检测到「决定守护」（或 `DeciKeeper` / 应用包名）。
- **拦截动作**：同时满足上述条件时，无障碍服务立即执行返回桌面操作（`GLOBAL_ACTION_BACK` + `GLOBAL_ACTION_HOME`）切断更改与卸载路径；
- **状态继承**：当防关权限保护处于 `DISABLED` 状态，或已获得短期授权放行时，上述防护自动停用，不影响正常设置。

## 5. 隐私空间拦截

### 5.1 目标

隐私空间拦截用于应对部分厂商 ROM 提供的隐私空间、原子隐私系统、隔离空间等路径。这些系统空间可能拥有独立应用列表或安装/添加入口，从而形成普通应用拦截链之外的绕过面。

### 5.2 状态机

`PrivacyProtectionManager` 当前状态：

| 状态 | 业务语义 | `isEnforcing()` |
| --- | --- | ---: |
| `DISABLED` | 关闭 | `false` |
| `ACTIVE` | 开启 | `true` |
| `PENDING` | 已申请关闭但未到期 | **`true`** |

当前规则：

- 开启：立即生效，并清除关闭 pending；
- 正常保护期关闭：严格下一业务日生效；
- 适应期，或基线本来就是关闭：立即关闭；
- `PENDING` 未到期期间必须继续拦截，不能因为 Switch 视觉已经显示“申请关闭”就提前放行。

### 5.3 OEM 路径

当前实现包含针对已确认 ROM 页面（如部分 Vivo / iQOO 隐私系统添加应用入口）的即时拦截，但这属于**兼容实现**而不是产品协议。

详细实现需要遵循：

- 用真实页面/窗口证据识别，而不是只靠单一易变文案；
- 开关关闭时不能继续拦截；
- 新增 OEM 适配必须有真机或可复核证据；
- 文档描述厂商示例时使用“如 / 当前已适配”，不写成所有 Android 设备通用能力。

## 6. 闹钟防关机保护

### 6.1 目标

闹钟防关机保护用于闹钟响铃/挑战期间，降低用户通过系统电源菜单直接关机来逃避起床流程的可能性。

### 6.2 当前开关规则

这是当前保护模块中的明确例外：

- 开启：**立即**；
- 关闭：**立即**；
- 不使用 `ACTIVE / PENDING / DISABLED` 三态；
- 不受「时间规则生效策略」影响。

因此不能为了统一文案，把它误写成“所有加强约束关闭都次日生效”。

### 6.3 前置能力

当前 `AlarmPowerOffProtectionManager` 检查的完整前置能力包括：

- 无障碍服务；
- 悬浮窗权限；
- 通知权限；
- 系统通知总开关可用；
- **“锁屏显示”确认位**：注意这是一个**本地人工确认位**（`lock_screen_display_confirmed`，见 `AlarmPowerOffProtectionManager`），由用户在引导弹窗内手动勾选写入 `SharedPreferences`，**不读取任何系统权限或 AppOp**；不得把它描述成“系统权限检查”。契约测试：`AlarmPowerOffProtectionManagerTest.lockScreenDisplayUsesIndependentManualConfirmation`。

缺失前置能力时，应明确提示缺失项，不得把仅保存了开关值描述成“保护已经完整工作”。

### 6.4 能力边界

该能力针对可由系统 UI / 无障碍链路感知和拦截的关机入口，不承诺阻止：

- 硬件长按强制关机；
- 强制重启组合键；
- 厂商未识别的私有电源路径；
- 系统在决定守护服务不可用时执行的底层关机行为。

## 7. 小窗可见性增强

### 7.1 目标

小窗 / 画中画（PIP）/ 分屏场景下，应用可能没有真实的全屏前台 Session，但仍占据可见区域。若完全不识别，"被管控的应用缩成小窗继续用"就会成为一条绕过路径。

本模块提供一个**显式开关**，决定是否把「无障碍窗口集合中的小窗可见性」纳入可用证据链。

### 7.2 状态机

由 `FloatingWindowProtectionManager` 承担，三态：

| 状态 | 含义 | `isEnforcing()` |
| --- | --- | --- |
| `DISABLED` | 未开启，或已到期的关闭已落地 | 否 |
| `ACTIVE` | 已开启且无待生效的关闭 | **是** |
| `PENDING` | 已开启，但有一个尚未到期的关闭待生效 | **是**（到期前保护不中断） |

- **开启（有利改动）**：**立即生效**，清空 pending。基准（Baseline）仅在适应期结束或配置生效时间刷新（如每日次日生效时刻）时由系统统一快照写入，严禁在手动开启时直接污染基准；
- **关闭（不利改动）**：默认走 `ConfigPendingManager` 的 `strictNextDay` 延迟；但以下两种情形**立即关闭**：
  1. 处于**适应期**；
  2. **baseline 中本项本来就是关闭的**（即恢复基准原则：恢复到本来就没有开启的状态）；
- **到期处理**：pending 时间到达后，`getProtectionState()` 会立即落库为关闭并清空 pending；
- **无障碍不可用**：`disableImmediatelyForAccessibilityUnavailable()` 立即关闭并清空 pending，跟随无障碍依赖清理。

### 7.3 真实生效点

判定入口是 `VisibleBlacklistPresenceTracker.hasAccessibilityBackedPresence()`：

1. 无障碍服务未激活 → 直接返回 `false`；
2. 服务已激活但 `isEnforcing()` 为假 → 直接返回 `false`；
3. 两者都成立时，才允许把 `CoreService.lastVisiblePackagesFromWindows` 的窗口集合当作"该包仍以小窗形式可见"的证据。

**普通全屏前台应用的 UsageEvents / ForegroundGuard 链路不经过这里，不受本开关影响。**

### 7.4 与 Baseline 例外的关系

本模块是**第三个**明确使用 baseline 例外的保护项（另两个是防卸载与隐私空间拦截）：关闭时若 baseline 中本项即为关闭，则立即生效而不进入 pending。

### 7.5 验收契约

`FloatingWindowProtectionManagerTest` 覆盖：初始态为 `DISABLED`；开启后立即 `ACTIVE` 且 `isEnforcing` 为真；无障碍不可用时立即禁用；baseline 为开启态时关闭进入 `PENDING` 且**仍然强制生效**；pending 到期后落地为 `DISABLED`。

---
## 8. 适应期、Baseline 与 Pending 的共同语义

保护功能不能只看当前 Switch 外观决定是否执行。

### 8.1 Baseline

Baseline 用于判断一次“关闭”到底是在削弱既有保护，还是只是恢复到本来就没有开启的状态。

当前明确使用 baseline 例外的保护包括：

- 防卸载；
- 隐私空间拦截；
- **小窗可见性增强**（同款 `!baselineEnabled` 即立即关闭的分支，见 `FloatingWindowProtectionManager`）。

### 8.2 适应期

适应期的目标是让用户在刚开始配置时可以纠错，不要因为初次试用就立刻把自己锁进不适合的配置。

当前防卸载和隐私空间关闭逻辑包含适应期立即生效例外。具体适应期时长属于实现参数，不在本文件写死为永久产品常量。

### 8.3 Pending

对于使用 delayed-disable 的保护：

- pending 只表示**关闭请求已经登记**；
- pending 未到期时，保护语义仍然有效；
- 到期后再落地到 `DISABLED`；
- 重新开启可以取消 pending。

---

## 9. 防绕过与可靠性原则

1. **不承诺绝对防绕过**：Android/OEM 允许用户拥有最终设备控制权，决定守护只能持续提高即时绕过成本。
2. **真实问题驱动适配**：对隐私空间、语言切换、特殊卸载路径、重启真空期、ROM 后台杀进程等真实发现的问题持续补强。
3. **关键路径不依赖单一文案**：厂商文案、语言和 View 层级容易变化，不能把某一字符串当作唯一保护证据。
4. **系统级白名单优先**：Launcher、当前输入法、电话/紧急呼叫、必要验证码等不能被普通黑名单逻辑误伤。
5. **证据失败不等于放行**：单次无障碍扫描失败、窗口树暂缺等不能直接伪造“应用已离开 / 保护已解除”。
6. **取证不反向控制业务**：诊断日志用于复盘，不得成为业务判定的真相源。
7. **真机优先**：涉及厂商设置页、隐私空间、小窗、电源菜单、重启恢复的修改，必须保留真机验证环节。

---

## 10. 当前验收契约

保护模块至少应由以下类型的测试/验证守护：

- 防卸载 `ACTIVE / PENDING / DISABLED` 流转；
- 防关权限 `PENDING` 期间仍保护；
- 隐私空间 `PENDING` 的 `isEnforcing() == true`；
- 隐私空间开关 OFF 时已适配 AddApp 路径不继续拦截；
- 小窗可见性增强 `DISABLED / ACTIVE / PENDING` 流转，且 `PENDING` 期间 `isEnforcing() == true`（到期前的保护不中断）；
- 无障碍不可用时小窗可见性增强被立即清空；
- 防卸载强行停止路径与普通卸载同等级处理；
- 无障碍列表页不会被决定守护整体误锁；
- 服务重连/锁屏代际变化后，普通规则锁能够重建，防卸载锁身份不会被普通请求降级；
- 闹钟防关机前置权限缺失时能准确报告缺失项；
- 涉及 OEM 系统页面的改动具备真机日志或明确验证记录。

---

## 11. 非目标

本模块不负责：

- 定义勿扰时段和应用时间窗——见后续 `focus.md`；
- 定义休息、临时解锁、每周特权的额度计算——见后续 `focus.md`；
- 定义闹钟挑战和第二阶段任务——见后续 `alarm.md`；
- 通过设备管理权永久阻止用户卸载；
- 宣称决定守护能对所有 Android / ROM 实现无法绕过的系统级控制。

## 12. 设置页与前置权限交互

设置页是底部五项导航中的第五项，不新增独立的“保护设置”页面。设置页必须保留现有的主题、黑白名单、全局参数、导出配置、导入配置、关于我们等入口，并将保护相关内容按以下层级展示：

```text
无障碍服务                         系统前置服务

加强约束功能                       可选增强
  闹钟防关机保护                     独立开关
  小窗可见性增强                     独立开关
  隐私空间保护                       独立开关
  防卸载与防关权限保护               合并开关
```

### 12.1 无障碍服务与增强功能的关系

- “无障碍服务”是系统权限前置项，不属于“加强约束功能”中的一个增强开关；
- “加强约束功能”下的闹钟防关机、小窗可见性增强、隐私空间保护可以分别选择；防卸载与防关权限保护使用一个合并开关，不提供把四项强制绑定开启的总开关；
- 四项增强功能的设置行统一提示“以下功能需先开启无障碍服务”。**目标契约**是每项在自己的 Manager 中再次检查实际前置条件；**当前实现与契约存在差距**：只有 `AlarmPowerOffProtectionManager` 在 Manager 内自查无障碍，`PrivacyProtectionManager` 与 `FloatingWindowProtectionManager` 内没有 a11y 判断，检查散落在 `RulesFragment`（`:534`、`:571`、`:2061`）；
- 无障碍服务关闭时，依赖它的增强功能不得显示为已经完整生效；
- 用户点击未满足前置条件的增强开关时，应先显示缺失条件和对应的系统设置入口，不得只保存一个看似开启的开关值；
- 系统无障碍被关闭后，四项依赖增强立即清除为 `DISABLED` / 关闭，不保留旧的 ACTIVE 状态；之后重新开启无障碍也不自动恢复，必须分别手动开启。

### 12.2 无障碍服务关闭顺序

防卸载与防关权限保护合并开关、无障碍服务之间存在操作顺序约束：

1. 合并开关开启时，同时开启防卸载与防关权限保护；
2. 合并开关关闭时，确认后同时提交两个保护的关闭申请，正常保护期均次日生效，适应期按各 Manager 的即时规则处理；
3. 用户准备关闭无障碍服务时，如果合并保护仍在执行，界面必须先协同提交两个保护的关闭申请，再允许继续处理无障碍服务关闭；
4. 不得允许用户先关闭无障碍服务、再留下仍声明开启的防卸载或防关权限保护；
5. 任一保护关闭申请处于 `PENDING`（“待关闭，明日生效”）时，该保护语义仍然有效；防卸载初始化界面仍允许显示；
6. 两项保护都为 `DISABLED` 后，关闭无障碍服务不再触发保护关闭流程。

开启无障碍服务只恢复系统前置能力，不自动开启防卸载、防关权限、小窗可见性、隐私空间或闹钟防关机增强；关闭无障碍时，才允许在同一次退出操作中协同提交当前仍在执行的增强关闭申请。

### 12.3 行级帮助入口

每个保护行的问号按钮必须紧邻开关左侧，且帮助内容只解释当前行：

- 无障碍服务：说明这是系统前置服务，以及关闭时需要先处理合并保护；
- 闹钟防关机保护：说明只在闹钟挑战期间工作，并列出无障碍、锁屏显示等前置条件；
- 小窗可见性增强：说明它增强小窗可见性识别；不使用“ROM 小窗”或“PIP”等面向用户的技术术语；
- 隐私空间保护：说明部分设备会存在独立空间的添加应用入口，当前保护是兼容性拦截，不宣称覆盖所有品牌；
- 防卸载与防关权限保护：说明它降低系统设置中直接卸载、强行停止和关闭关键权限的即时绕过概率，并说明语言切换或服务重连时可能出现短暂初始化/预热；

“导出日志”与“隐藏知止在多任务界面”保持为独立设置区块；当前不新增“查看日志”入口。

### 12.4 闹钟防关机保护的开启流程

闹钟防关机保护仍是置顶独立开关，开启和关闭均立即生效，不受时间规则的次日策略影响。开启时按以下顺序检查：

1. 无障碍服务已开启并处于可用连接状态；
2. 悬浮窗、通知及系统通知总开关满足当前实现要求；
3. 闹钟通知允许显示在锁屏上。

缺少任一条件时：

- 开关保持关闭；
- **无障碍服务缺失时只弹 Toast 并直接返回，不进入引导弹窗**（`RulesFragment.kt:1103-1109`）；引导弹窗只覆盖非无障碍的前置条件（`:1110-1117`）；
- 弹窗明确列出缺失条件；
- 用户点击“去开启”进入对应系统设置；
- 从系统设置返回后重新检查全部条件；
- 只有全部条件满足时，才将开关更新为开启。

设置页不增加一个长期独立的“锁屏显示”业务开关；它作为闹钟防关机保护的**人工确认项**，放在权限引导中按需处理。

### 12.5 防卸载与防关权限合并开关

合并开关开启前必须先检查无障碍服务。若锁屏显示权限未授予，仍允许用户选择是否继续：

- **开启锁屏显示**：跳转应用权限设置，返回后重新检查，保护不会在跳转前静默开启；
- **不开锁屏，仍要开启**：在无障碍服务可用时，同时立即开启防卸载与防关权限保护；
- 合并开关关闭时**不弹确认框**，直接同时调用两个 Manager 的关闭接口（原「冷静期温情确认」弹窗已移除，由 `RulesSettingsUiContractTest` 反向锁死其不存在）；正常保护期显示 `状态: 待关闭（明日生效）`，适应期按 Manager 规则立即关闭。

### 12.6 防卸载初始化界面门禁

现有防卸载初始化界面只属于防卸载与防关权限合并保护的运行链路：

- 防卸载为 `ACTIVE` 时允许显示；
- 防卸载为 `PENDING`（待关闭，明日生效）时仍允许显示；
- 防卸载为 `DISABLED` 时不得因为无障碍服务开启、其他增强开启、配置变更或闹钟流程而显示；
- 小窗可见性增强、隐私空间保护或闹钟防关机保护单独开启时，不得触发防卸载初始化界面；
- 初始化/预热界面出现时不得把防卸载状态错误改写为 `DISABLED`，也不得绕过 `PENDING` 的继续保护语义；
- 用户首次解锁前（Direct Boot）不显示初始化界面、不读取任何 CE 存储（含主题偏好），解锁后立即按同一门禁补挂；统一入口为 `StartupProtectionManager.triggerBootFastLock`，多通道（Application / `USER_UNLOCKED` / 无障碍连接 / `BOOT_COMPLETED`）先到先得、只挂一次。

### 12.7 设置页验收契约

- 设置页仍位于底部导航第五项，原有设置入口完整保留；
- “无障碍服务”位于“加强约束功能”区块之前，并作为四项增强功能的前置项展示；
- 四项增强按“闹钟防关机保护、小窗可见性增强、隐私空间保护、防卸载与防关权限保护”的顺序展示；
- 每个问号均位于对应开关左侧，点击后只打开对应说明；
- 防卸载与防关权限合并开关在无障碍关闭时不能直接开启；
- 关闭无障碍时不能绕过合并保护的协同关闭顺序；
- 闹钟保护缺少锁屏显示时不能显示为已开启；
- 合并开关缺少锁屏显示时必须显示前置提示，并提供继续开启分支；
- 四项状态文案统一为 `状态: 已开启`、`状态: 未开启` 或 `状态: 待关闭（明日生效）`，闹钟保护不出现待关闭状态；
- 防卸载为 `PENDING` 时初始化界面仍可显示，`DISABLED` 时不显示；
- 不出现“查看日志”入口，也不把导出日志与多任务隐藏放进同一个功能区块。
