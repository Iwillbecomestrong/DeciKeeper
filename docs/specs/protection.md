# 加强约束与保护机制规格

> **职责**：本文件定义决定守护当前「加强约束功能」的详细产品契约、状态语义与系统边界。
>
> 根 [`SPEC.md`](../../SPEC.md) 只保留跨模块原则；本文件是保护模块的详细规格。Android/OEM 页面识别细节以当前代码与测试为实现证据，不能把某一厂商当前页面结构当作永久平台协议。

---

## 1. 模块定位

加强约束功能的目的不是永久阻止用户退出，而是：

> **降低用户通过卸载、关闭关键权限、隐私空间或关机等路径，立刻推翻此前决定的可能性。**

这些功能与「时间规则」是两个层级：

- **时间规则**回答：勿扰时段和应用时间窗什么时候工作；
- **加强约束**回答：已经决定好的规则如何降低被系统入口即时绕过的概率。

因此：

1. 「宽严有别 / 全部次日」**只属于时间规则**；
2. 防卸载、防关权限、隐私空间、闹钟防关机分别遵循自己的状态机；
3. 不承诺“绝对不可绕过”，只持续补强真实发现的绕过路径；
4. 所有保护必须保留用户最终退出权。

---

## 2. 无障碍服务：技术基础，不是时间规则

Android 无障碍服务是多个保护能力和前台可见性感知的执行基础。

当前职责包括但不限于：

- bu'zhi'd接收前台窗口/内容变化事件；
- 获取可用的窗口树和可见应用信息；
- 辅助小窗、分屏、PIP 等场景的 Presence Tracking；
- 识别与决定守护相关的系统设置、卸载、强行停止、权限关闭、隐私空间等页面；
- 在符合具体保护开关门禁时执行返回桌面、覆盖层或其他拦截动作。

### 2.1 两个概念必须分开

| 概念 | 含义 |
| --- | --- |
| **系统无障碍服务** | Android 系统真正授予/撤销的 AccessibilityService 权限与服务连接状态 |
| **防关权限保护** | 决定守护内部的业务保护状态，用于降低用户立即关闭关键无障碍权限的可能 |

`AccessibilityControlManager` 不直接替用户修改 Android 的系统开关；它维护的是业务侧 `ACTIVE / PENDING / DISABLED` 状态。

### 2.2 降级边界

无障碍不可用、未连接或被 ROM 异常杀死时：

- 依赖窗口树和系统设置页识别的保护能力会下降；
- UsageStats / 轮询等其他前台证据可以继续提供部分基础能力，但不得把降级路径宣传成与无障碍完全等价；
- UI 和诊断必须能够区分“服务未就绪”与“规则已经正常执行”。

## 3. 防卸载保护

### 3.1 目标

防卸载保护用于降低通过系统应用信息页、卸载确认、强行停止等路径即时移除或停用决定守护的可能性。

它保护的核心不是“永远不允许卸载”，而是：

> **不让一时冲动立刻把保护本身拆掉。**

### 3.2 状态机

`AntiUninstallManager` 当前状态：

| 状态 | 业务语义 | 是否继续保护 |
| --- | --- | --- |
| `DISABLED` | 防卸载关闭 | 否 |
| `ACTIVE` | 防卸载正常开启 | 是 |
| `PENDING` | 已申请关闭，等待严格下一业务日生效 | **是** |

状态流转：

- `DISABLED → ACTIVE`：立即；
- `ACTIVE → PENDING`：正常保护期内申请关闭；
- `PENDING → DISABLED`：到达 pending 生效时刻；
- `PENDING → ACTIVE`：用户重新开启时取消 pending；
- 适应期内关闭，或只是恢复到“基线本来就是关闭”的状态：可直接进入 `DISABLED`。

正常保护期的关闭使用 `strictNextDay = true`，避免凌晨提交后在同一个自然日上午就提前放开。

### 3.3 当前执行范围

当前实现持续维护以下防绕过路径：

- 决定守护应用信息/卸载相关系统入口；
- 强行停止相关系统对话框；
- 决定守护自身无障碍详情/停止服务相关入口；
- 进程启动、服务重连与 OEM 页面切换中的短暂真空期；
- 与隐私空间相关的已确认特殊入口。

强行停止与普通卸载属于同等级的重要绕过入口，不能因为对话框文字、厂商样式或焦点变化就降级为仅靠文本猜测。

### 3.4 无障碍页面边界

普通“无障碍服务列表”不能被决定守护整体锁死，否则会妨碍用户管理其他 App 的无障碍服务。

保护应聚焦于：

- 决定守护自己的无障碍详情页；
- 停止/关闭决定守护服务的确认路径；
- 已确认会直接削弱决定守护保护链的系统入口。

---

## 4. 防关权限保护

### 4.1 目标

防关权限保护用于降低用户直接进入系统设置，把决定守护赖以执行规则的关键无障碍能力立即关闭的可能性。

### 4.2 状态机

`AccessibilityControlManager` 当前状态：

| 状态 | 业务语义 | 是否继续保护 |
| --- | --- | --- |
| `ACTIVE` | 防关权限保护开启 | 是 |
| `PENDING` | 已申请关闭，尚未到生效时刻 | **是** |
| `DISABLED` | 业务保护关闭 | 否 |

当前规则：

- 开启：立即生效并清除旧 pending；
- 关闭：提交严格下一业务日的 pending；
- pending 到期后落地为 `DISABLED`；
- `PENDING` 期间系统设置页保护仍按开启状态执行。

### 4.3 与防卸载的协同关闭

用户不需要“今天先关防卸载、明天才能申请关无障碍”。当前产品允许在一次退出意图中同时提交防卸载和防关权限的关闭申请，让二者分别按照自己的 pending 生效时刻收束。

这体现的仍是同一原则：

> **允许退出，但不给冲动提供逐层秒拆保护链的捷径。**

---

## 5. 隐私空间拦截

### 5.1 目标

隐私空间拦截用于应对部分厂商 ROM 提供的隐私空间、原子隐私系统、隔离空间等路径。这些系统空间可能拥有独立应用列表或安装/添加入口，从而形成普通应用拦截链之外的绕过面。

### 5.2 状态机

`PrivacyProtectionManager` 当前状态：

| 状态 | 业务语义 | `isEnforcing()` |
| --- | --- | ---: |
| `DISABLED` | 关闭 | `false` |
| `ACTIVE` | 开启 | `true` |
| `PENDING` | 已申请关闭但未到期 | **`true`** |

当前规则：

- 开启：立即生效，并清除关闭 pending；
- 正常保护期关闭：严格下一业务日生效；
- 适应期，或基线本来就是关闭：立即关闭；
- `PENDING` 未到期期间必须继续拦截，不能因为 Switch 视觉已经显示“申请关闭”就提前放行。

### 5.3 OEM 路径

当前实现包含针对已确认 ROM 页面（如部分 Vivo / iQOO 隐私系统添加应用入口）的即时拦截，但这属于**兼容实现**而不是产品协议。

详细实现需要遵循：

- 用真实页面/窗口证据识别，而不是只靠单一易变文案；
- 开关关闭时不能继续拦截；
- 新增 OEM 适配必须有真机或可复核证据；
- 文档描述厂商示例时使用“如 / 当前已适配”，不写成所有 Android 设备通用能力。

---

## 6. 闹钟防关机保护

### 6.1 目标

闹钟防关机保护用于闹钟响铃/挑战期间，降低用户通过系统电源菜单直接关机来逃避起床流程的可能性。

### 6.2 当前开关规则

这是当前保护模块中的明确例外：

- 开启：**立即**；
- 关闭：**立即**；
- 不使用 `ACTIVE / PENDING / DISABLED` 三态；
- 不受「时间规则生效策略」影响。

因此不能为了统一文案，把它误写成“所有加强约束关闭都次日生效”。

### 6.3 前置能力

当前 `AlarmPowerOffProtectionManager` 检查的完整前置能力包括：

- 无障碍服务；
- 悬浮窗权限；
- 通知权限；
- 系统通知总开关可用；
- 系统“锁屏显示”应用权限；不把通知权限或全屏意图权限替代这项检查。

缺失前置能力时，应明确提示缺失项，不得把仅保存了开关值描述成“保护已经完整工作”。

### 6.4 能力边界

该能力针对可由系统 UI / 无障碍链路感知和拦截的关机入口，不承诺阻止：

- 硬件长按强制关机；
- 强制重启组合键；
- 厂商未识别的私有电源路径；
- 系统在决定守护服务不可用时执行的底层关机行为。

---

## 7. 适应期、Baseline 与 Pending 的共同语义

保护功能不能只看当前 Switch 外观决定是否执行。

### 7.1 Baseline

Baseline 用于判断一次“关闭”到底是在削弱既有保护，还是只是恢复到本来就没有开启的状态。

当前明确使用 baseline 例外的保护包括：

- 防卸载；
- 隐私空间拦截。

### 7.2 适应期

适应期的目标是让用户在刚开始配置时可以纠错，不要因为初次试用就立刻把自己锁进不适合的配置。

当前防卸载和隐私空间关闭逻辑包含适应期立即生效例外。具体适应期时长属于实现参数，不在本文件写死为永久产品常量。

### 7.3 Pending

对于使用 delayed-disable 的保护：

- pending 只表示**关闭请求已经登记**；
- pending 未到期时，保护语义仍然有效；
- 到期后再落地到 `DISABLED`；
- 重新开启可以取消 pending。

---

## 8. 防绕过与可靠性原则

1. **不承诺绝对防绕过**：Android/OEM 允许用户拥有最终设备控制权，决定守护只能持续提高即时绕过成本。
2. **真实问题驱动适配**：对隐私空间、语言切换、特殊卸载路径、重启真空期、ROM 后台杀进程等真实发现的问题持续补强。
3. **关键路径不依赖单一文案**：厂商文案、语言和 View 层级容易变化，不能把某一字符串当作唯一保护证据。
4. **系统级白名单优先**：Launcher、当前输入法、电话/紧急呼叫、必要验证码等不能被普通黑名单逻辑误伤。
5. **证据失败不等于放行**：单次无障碍扫描失败、窗口树暂缺等不能直接伪造“应用已离开 / 保护已解除”。
6. **取证不反向控制业务**：诊断日志用于复盘，不得成为业务判定的真相源。
7. **真机优先**：涉及厂商设置页、隐私空间、小窗、电源菜单、重启恢复的修改，必须保留真机验证环节。

---

## 9. 当前验收契约

保护模块至少应由以下类型的测试/验证守护：

- 防卸载 `ACTIVE / PENDING / DISABLED` 流转；
- 防关权限 `PENDING` 期间仍保护；
- 隐私空间 `PENDING` 的 `isEnforcing() == true`；
- 隐私空间开关 OFF 时已适配 AddApp 路径不继续拦截；
- 防卸载强行停止路径与普通卸载同等级处理；
- 无障碍列表页不会被决定守护整体误锁；
- 服务重连/锁屏代际变化后，普通规则锁能够重建，防卸载锁身份不会被普通请求降级；
- 闹钟防关机前置权限缺失时能准确报告缺失项；
- 涉及 OEM 系统页面的改动具备真机日志或明确验证记录。

---

## 10. 非目标

本模块不负责：

- 定义勿扰时段和应用时间窗——见后续 `focus.md`；
- 定义休息、临时解锁、每周特权的额度计算——见后续 `focus.md`；
- 定义闹钟挑战和第二阶段任务——见后续 `alarm.md`；
- 通过设备管理权永久阻止用户卸载；
- 宣称决定守护能对所有 Android / ROM 实现无法绕过的系统级控制。

## 11. 设置页与前置权限交互

设置页是底部五项导航中的第五项，不新增独立的“保护设置”页面。设置页必须保留现有的主题、黑白名单、全局参数、导出配置、导入配置、关于我们等入口，并将保护相关内容按以下层级展示：

```text
无障碍服务                         系统前置服务

加强约束功能                       可选增强
  小窗可见性识别与防关权限保护       独立开关
  隐私空间保护                       独立开关
  防卸载增强                         独立开关
  闹钟防关机保护                     独立开关
```

### 11.1 无障碍服务与增强功能的关系

- “无障碍服务”是系统权限前置项，不属于“加强约束功能”中的一个增强开关；
- “加强约束功能”下的四项能力可以分别选择，不提供一个把四项强制绑定开启的总开关；
- 四项增强功能的设置行可以统一提示“以下功能需先开启无障碍服务”，但每项仍必须在自己的 Manager 中再次检查实际前置条件；
- 无障碍服务关闭时，依赖它的增强功能不得显示为已经完整生效；
- 用户点击未满足前置条件的增强开关时，应先显示缺失条件和对应的系统设置入口，不得只保存一个看似开启的开关值；
- 系统无障碍被关闭后，四项依赖增强立即清除为 `DISABLED` / 关闭，不保留旧的 ACTIVE 状态；之后重新开启无障碍也不自动恢复，必须分别手动开启。

### 11.2 无障碍服务关闭顺序

防卸载增强与无障碍服务之间存在不可逆的操作顺序约束：

1. 防卸载增强可以在无障碍服务保持开启时单独开启或关闭；
2. 用户准备关闭无障碍服务时，如果防卸载仍为 `ACTIVE`，界面必须先提交防卸载关闭申请，再允许继续处理无障碍服务关闭；
3. 不得允许用户先关闭无障碍服务、再留下仍声明开启的防卸载增强；
4. 防卸载关闭申请处于 `PENDING`（“待关闭，明日生效”）时，防卸载保护语义仍然有效；其初始化界面仍允许显示；
5. 防卸载已经是 `DISABLED` 后，关闭无障碍服务不再触发防卸载关闭流程。

开启无障碍服务只恢复系统前置能力，不自动开启防卸载、防关权限、隐私空间或闹钟防关机增强；关闭无障碍时，才允许在同一次退出操作中协同提交这些增强的关闭申请。

### 11.3 行级帮助入口

每个保护行的问号按钮必须紧邻开关左侧，且帮助内容只解释当前行：

- 无障碍服务：说明这是系统前置服务，以及关闭时需要先处理防卸载；
- 小窗可见性识别与防关权限保护：说明它增强小窗可见性识别，并保护已识别的关键权限页面；不使用“ROM 小窗”或“PIP”等面向用户的技术术语；
- 隐私空间保护：说明部分设备会存在独立空间的添加应用入口，当前保护是兼容性拦截，不宣称覆盖所有品牌；
- 防卸载增强：说明它降低系统设置中直接卸载、强行停止和关闭关键服务的即时绕过概率，并说明语言切换或服务重连时可能出现短暂初始化/预热；
- 闹钟防关机保护：说明只在闹钟挑战期间工作，并列出无障碍、锁屏显示等前置条件。

“导出日志”与“隐藏知止在多任务界面”保持为独立设置区块；当前不新增“查看日志”入口。

### 11.4 闹钟防关机保护的开启流程

闹钟防关机保护仍是独立开关，开启和关闭均立即生效，不受时间规则的次日策略影响。开启时按以下顺序检查：

1. 无障碍服务已开启并处于可用连接状态；
2. 悬浮窗、通知及系统通知总开关满足当前实现要求；
3. 闹钟通知允许显示在锁屏上。

缺少任一条件时：

- 开关保持关闭；
- 弹窗明确列出缺失条件；
- 用户点击“去开启”进入对应系统设置；
- 从系统设置返回后重新检查全部条件；
- 只有全部条件满足时，才将开关更新为开启。

设置页不增加一个长期独立的“锁屏显示”业务开关；锁屏显示属于系统应用权限，放在闹钟防关机保护的权限引导中按需处理。防卸载增强不依赖锁屏显示。

### 11.5 防卸载初始化界面门禁

现有防卸载初始化界面只属于防卸载增强的运行链路：

- 防卸载为 `ACTIVE` 时允许显示；
- 防卸载为 `PENDING`（待关闭，明日生效）时仍允许显示；
- 防卸载为 `DISABLED` 时不得因为无障碍服务开启、其他增强开启、配置变更或闹钟流程而显示；
- 小窗可见性识别、防关权限保护、隐私空间保护或闹钟防关机保护单独开启时，不得触发防卸载初始化界面；
- 初始化/预热界面出现时不得把防卸载状态错误改写为 `DISABLED`，也不得绕过 `PENDING` 的继续保护语义。

### 11.6 设置页验收契约

- 设置页仍位于底部导航第五项，原有设置入口完整保留；
- “无障碍服务”位于“加强约束功能”区块之前，并作为四项增强功能的前置项展示；
- 四项增强按“小窗可见性识别与防关权限保护、隐私空间保护、防卸载增强、闹钟防关机保护”的顺序展示；
- 每个问号均位于对应开关左侧，点击后只打开对应说明；
- 防卸载在无障碍关闭时不能直接开启；
- 关闭无障碍时不能绕过防卸载关闭顺序；
- 闹钟保护缺少锁屏显示时不能显示为已开启；
- 防卸载为 `PENDING` 时初始化界面仍可显示，`DISABLED` 时不显示；
- 不出现“查看日志”入口，也不把导出日志与多任务隐藏放进同一个功能区块。
