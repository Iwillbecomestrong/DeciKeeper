# 决定守护 DeciKeeper 产品总览

本文件解释“为什么这样设计”；当前行为以 [SPEC.md](../../SPEC.md) 与 [模块规格](../specs/) 为准。

## 产品从两个具体问题开始

决定守护不是先从抽象的“决定保护系统”开始。它先解决两件长期、具体的事：

```text
该开始做事时，手机一拿起来停不下来
该起床时，闹钟按掉又继续睡
                ↓
             决定守护
        ├── 时间规则
        └── 挑战闹钟
```

两个模块独立启用，但都来自作者自己的真实使用问题。

## 时间规则：修改行为与生效行为分离

现有方案常落在两个极端：让调整规则本身很麻烦，但真正想放宽时仍可等完后立即放宽；或规则很死，却没有正常生活所需的出口。

作者试过系统限额、专注模式、番茄钟和一些限制 App 的软件，遇到的正是这两个问题：

- **改起来很麻烦，却没有真正限制住。**手输一长串不能复制的字符，或等一分钟，真想玩时仍然愿意做；等完又能马上放宽，最后还是继续玩。正常调整规则时，也得承受同样的摩擦。
- **管得特别死，正常有事时又没有出口**，反而很容易用不下去。

所以想要的是：**修改本身方便，正常有事时有出口；但已经生效的规则，不能因为一次放宽马上被冲掉。**

决定守护不尝试判断一次修改来自正常计划、临时冲动、情绪变化还是作息调整；这些动机无法由一次设置操作可靠判断。它真正区分的是：

1. 用户修改了配置；
2. 配置保存成功；
3. 这个配置何时改变当前有效规则。

修改保持低成本。相对于当前稳定基准，更严格的修改可以立即作用；更宽松的修改先保存、在后续生效时点进入稳定规则；恢复当前稳定基准属于即时纠错。

例如当前稳定规则是一小时，改成半小时是加严，可以立即生效，新规则成为稳定规则前发现不合适也可以立即恢复一小时；改成两小时同样可以立即保存，但不会立刻多出这一小时，生效前仍可继续修改或取消。

设计目标不是把“改规则”做得很难，而是：**让正常调整保持方便，同时不给一次放宽立即改变当前状态的能力。**

### 两把锁为何逐步形成

第一把**勿扰锁**解决的是学习、工作或睡眠时别一直刷手机。休息、休息次数与时长、同一业务日额度结余/借用、每周特权，都是为了让正常生活有出口。

后来发现游戏等特别容易连续使用超时的应用，只靠休息不够：临时摸鱼会耗尽休息额度甚至每周特权，真正有事时反而没有出口。因此出现第二把**应用时间窗锁**：普通休息可以临时决定，但高风险应用最好提前决定什么时候玩。

**现在可以休息，不代表现在就可以打游戏。**休息只解除勿扰锁，不能解除应用时间窗。

### 三个出口

| 出口 | 定位 | 权能 |
| --- | --- | --- |
| 休息 | 日常正常放松 | 只解除勿扰锁 |
| 临时解锁 | 极短应急 | 最长 3 分钟，短暂越过两把锁 |
| 每周特权 | 少数特殊情况 | 较长时间越过两把锁；按周提前配置（次周生效，上限为每周 3 次、累计最长 10 小时，具体以周配置为准） |

**三个出口负责灵活；两把锁和加强约束负责严格；生效机制让规则方便调整，又不会因一次放宽马上失效。**

## 挑战闹钟的设计来源

扫码离床并不是 DeciKeeper 原创。作者大学住上床下桌时，把手机放在下面、让自己必须下床关闹钟，对起床很有效；后来手机放到床边，又开始按掉闹钟继续睡。通过 GPT 查询现有方案时了解到 QRAlarm，因此参考了扫码离床的已有思路：二维码放在洗手台、客厅等离床的位置，真正起作用的是物理距离。

最小 demo 很快就能“响、扫码、关”，真正花时间的是扫码鲁棒性、锁屏 / 后台、重启恢复，以及降低从关机或重启绕过流程的可能。

DeciKeeper 的重点不是宣称发明扫码闹钟，而是在自身场景中整合离床验证、多种挑战（扫码、计算、单词、诗词、选词填空）、自定义题库、有限延迟、完成后的缓冲、可选后续阶段、每月次数有限的应急退出，以及 Android 上的锁屏、后台、重启恢复与相关保护能力。后续扩展都应表述为“根据自己的使用需求继续调整”，而非把已有挑战闹钟概念包装成原创。

## 保护与边界

加强保护的目标是提高当场拆掉已生效规则的难度，不承诺绝对无法绕过。它必须允许最终退出；不同 Android 品牌和 ROM 的可靠性边界也必须如实说明。闹钟防关机是独立即时开关，不能为统一宣传而误写成所有保护都延后关闭。
