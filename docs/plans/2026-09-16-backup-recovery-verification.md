## 2. 已讨论的调整方向与边界

| 项目 | 方向 | 前置条件 |
| --- | --- | --- |
| 内部自动备份 | 保留默认启用与双快照 | 核实写入、轮转和失败行为 |
| 外部自动备份 | 首次明确告知位置、内容、卸载后保留方式，并提供控制入口 | 核实目标 Android / ROM 上实际存储访问能力 |
| 重装恢复 | 先核实现有读取路径；后续考虑发现备份后展示摘要、由用户确认恢复 | 不将自动恢复成功当作当前事实；确认与初始化、保护恢复链的关系 |
| 系统云备份 | 按严格本地隐私定位，拟关闭 | 实施时核对不同 Android 版本的备份规则 |
| 换机迁移 | 单独决定 | 尚未确定策略，不与云备份一并推定关闭 |
| 旧备份与手动导入 | 保留兼容读取和现有手动入口，不能静默丢弃 | 保留历史格式、目录和字段迁移能力 |

本次只更新文档，不代表上述行为已经实现。未核实前不删除自动读取路径，不修改业务默认值，不通过导入绕过 Active / Baseline / Pending 规则。

## 3. 核验步骤

1. 确认测试 APK 的版本、源码提交、签名及与当前工作区的差异。
2. 在隔离测试环境触发规则变更与备份，分别检查内部和公共目录的实际文件、时间、大小及解析结果；不要输出真实备份内容到公开日志。
3. 分别核对首次安装、已有配置、清空测试数据、重装后的 `isFreshInstall()` 判定，以及初始化是否提前写入判定所需键。
4. 记录公共目录访问权限、候选文件是否存在、能否读取、解析或应用失败的位置；区分未触发、无文件、无权限、格式不兼容及恢复失败。
5. 检查自动恢复调用与隐私同意、Direct Boot、保护恢复、闹钟初始化的顺序，避免对既有防御产生影响。
6. 检查备份结果日志：内部或外部失败须分别报告；两处失败不得报告成功。现有汇总成功日志不能单独证明实际落盘。

重装与卸载场景使用测试设备或独立测试包；禁止卸载用户日常应用、清除真实数据来复现。

## 4. 后续实现范围

- `AutoBackupManager.kt`：核验触发、存储、轮转、结果报告及恢复入口。
- `SettingsBackupManager.kt`：核验完整解析、格式版本、字段和数值校验、失败时的数据保持、旧协议迁移及受保护规则处理。
- `MyApplication.kt`：核验恢复与初始化调用顺序。
- 备份设置 UI：按核验结论补告知、控制与恢复摘要，不凭计划假定现有入口状态。
- `backup_rules.xml` / `data_extraction_rules.xml` / Manifest：分别处理系统云备份与换机迁移策略。
- `docs/specs/data.md`、`docs/user/permissions.md`、隐私政策和隐私说明：随已实现行为同步，区分私有存储、公共备份、系统备份及手动导出。

不采用只依赖本机 Keystore、却无法跨重装解密的方案冒充可恢复备份；普通校验和只能检测损坏，不能作为防篡改证明。

## 5. 验收标准

- 给出用户仍需手动导入的可复现原因；证据不足则明确未确认。
- 内部与外部写入状态可分别核对，失败不误报成功。
- 损坏或不兼容文件导入失败时原数据保持完整；旧格式合法备份可导入。
- 覆盖无外部访问权限、磁盘写入失败、损坏 JSON、超大文件、恢复中断与已有有效保护场景。
- 导入不意外放宽现有保护，恢复不带入旧隐私同意状态。
- 用户文档与实际 APK 行为一致；系统云备份和换机迁移分别记录验证结果。
- 实现后运行受影响测试、全量 JVM 测试与 Release 构建；OEM 存储和重装效果单列真机结果。
