# 贡献者文档与模块边界收敛计划

状态：入口文档、用户帮助同步约定和两个可测试边界已收敛；最终 Release/真机证据完成后再归档。日期：2026-09-16。

## 目标与范围

外部贡献者能按文档完成构建、定位业务、验证修改和准备 PR。当前存在 dev/main 流程、Debug/Release 安装、旧渠道地址及设备管理器描述冲突；远端分支与下载有效性需实时核验。大文件行数只提示审查成本，不作为整体重构依据。

范围：README.md、AGENT_CORE.md、app/README.md、.github/CONTRIBUTING.md、PR/Issue 模板、docs/PUBLISHING.md、docs/ARCHITECTURE.md、用户说明及相关 scoped spec。核心大文件只在独立行为明确、测试可对照时做后续小范围提取。

## 文档步骤

1. 以当前 Git、workflow 和实际发布规则建立冲突表：现有说法、实现证据、拟修正内容、权威归属。
2. 查询实际 remote、远端分支、默认分支和 CI 覆盖；明确当前贡献目标，不能仅因当前 checkout 为 dev 就规定所有 PR 去 dev。
3. 统一开发构建与日常设备部署说明：贡献者 Debug 构建可用；正式设备更新优先签名一致的 Release，禁止通过卸载解决签名冲突。
4. 核对下载与源码链接是否有效、是否有重定向；品牌旧名在兼容键、协议与历史证据中保留，不做全仓替换。
5. 用户手册修正指定/任意 QR、权限撤销、延期退出、设备管理器及备份去向的冲突；以已核实行为为依据，未实施方案留在 plans。
6. PR 模板区分规则域，不将所有放宽都机械指向同一个 pending key；要求影响范围、验证状态和 OEM 未验证项。
7. 新贡献者最短入口包含 SDK/JDK、clone 后配置、构建和测试命令、输出路径、模块定位、问题报告方式。避免增加与 SPEC 竞争的全量规则文档。
8. 检查用户帮助进入 APK 的同步机制；用户手册变化运行对应现有契约并构建确认资产。

## 模块提取步骤（后续独立批次）

1. 先画实际调用关系，选取已有重复判断或本次需修改的边界。
2. 优先从 RulesFragment 提取设备管理器 UI 状态映射；从备份流程提取校验/结果表示；复用现有类，不增加只有一个实现的接口层。
3. 提取前建立输入输出与副作用对照，保留线程、时间基准、持久化顺序、OEM 判断及失败行为。
4. 一批只提取一个边界；不同时修改 CreditManager、MonitorService、LockWindowManager 的业务语义。
5. 用既有测试及必要行为用例验证等价；变化涉及运行链时补真机测试。没有可证明收益的拆分不执行。

## 验收与依赖

- 从干净 checkout 按贡献指南可构建和运行测试；权限说明与最终行为一致。
- 文档链接检查通过；所有建议有计划归属，所有“已完成”都有证据。
- 规则只有一个权威文档，各入口以链接引用。
- 模块提取前后行为一致，未降低防绕过强度，未改变真实数据或统计口径。
- 依赖 OEM/备份计划确认产品行为，Release/质量计划确定操作命令；先修事实冲突，最后收敛入口文本。
